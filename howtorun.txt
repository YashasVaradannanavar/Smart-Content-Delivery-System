HOW TO RUN simple_scdn.py
=========================

Everything below is on Ubuntu (WSL2 or a normal Ubuntu machine). The project
lives in ~/smart-content-delivery. You need sudo, because Mininet creates
network namespaces.


QUICK START (3 commands)
------------------------
    cd ~/smart-content-delivery
    sudo python3 simple_scdn.py
    column -s, -t results/simple_scdn_results.csv

The run takes well under a minute and prints nine blocks: STEP 0 to STEP 7,
then a SUMMARY. You need nothing else: no controller, no pip install, no venv.


STEP 1 - OPEN A WSL/UBUNTU TERMINAL
-----------------------------------
  From Windows: open "Ubuntu" from the Start menu, or run

      wsl.exe -d Ubuntu

  Then:

      cd ~/smart-content-delivery
      ls

  You should see simple_scdn.py, README.txt, howtorun.txt and results/.


STEP 2 - CHECK THE TOOLS (once, optional but recommended)
---------------------------------------------------------
    python3 --version                 # 3.8 or newer
    mn --version                      # Mininet
    ovs-vsctl --version               # Open vSwitch, 2.x or newer
    sudo service openvswitch-switch status

If "ovs-vsctl" complains that it cannot connect to the database, start the
service first:

    sudo service openvswitch-switch start

Nothing needs to be installed from pip. The script imports only the Python
standard library plus Mininet itself.


STEP 3 - RUN IT
---------------
    sudo python3 simple_scdn.py

It writes results/ into the folder that contains simple_scdn.py, so the
starting directory does not matter. Nothing else is required - no flags, no
config file.

To also keep a log of the run (handy for a report):

    sudo python3 simple_scdn.py 2>&1 | tee run.log

STEP 6 - WATCH THE SWITCH YOURSELF (optional, nice during a demo)
-----------------------------------------------------------------
The switch only exists while the script runs, so open two terminals:

  Terminal 1:
      sudo python3 simple_scdn.py

  Terminal 2 (while step 3/6 is running):
      sudo ovs-ofctl -O OpenFlow13 dump-flows s1
      sudo ovs-ofctl -O OpenFlow13 show s1

Every time the VIP rule is re-pointed you will see the set_field MAC and the
output port change, and n_packets on that rule keep growing. Ctrl-C in terminal
1 ends the demo; the script tears the network down itself.

Note: Open vSwitch refreshes counters about once a second, so a rule used a
moment ago can still read n_packets=0 for a fraction of a second.


STEP 7 - RUN IT AGAIN / CLEAN UP
--------------------------------
Just run it again - it deletes the old switch and interfaces at startup:

    sudo python3 simple_scdn.py

If you interrupted a run and want to be sure nothing is left:

    sudo ovs-vsctl --if-exists del-br s1
    sudo mn -c                    # Mininet's own cleanup

Check it is clean:

    sudo ovs-vsctl show            # s1 should be gone
    ip -br link | grep -E 's1-eth|h[1-4]-eth0'   # no output


STEP 8 - RUN IT FROM WINDOWS WITHOUT ENTERING WSL
-------------------------------------------------
    wsl.exe -u root -d Ubuntu -- bash -lc "cd /home/<user>/smart-content-delivery && python3 simple_scdn.py"

Then open results/simple_scdn_results.csv from Windows Explorer at
\\wsl.localhost\Ubuntu\home\<user>\smart-content-delivery\results\


TROUBLESHOOTING
---------------
  "Mininet needs root.  Run:  sudo python3 simple_scdn.py"
      You forgot sudo. The script exits with an error on purpose.

  "required program not found: ovs-ofctl" (or mn, ovs-vsctl)
      Open vSwitch or Mininet is not installed/visible in PATH:
          sudo apt install mininet openvswitch-switch

  ovs-vsctl: database connection failed
      The OVS service is not running:
          sudo service openvswitch-switch start

  "the web server on h3 did not start" / port 8080 already in use
      Something else is listening on 8080 inside the namespace, usually a
      leftover server from an interrupted run. Clean up and retry:
          sudo mn -c
      To use another port, change HTTP_PORT at the top of simple_scdn.py.

  "switch port for hX (s1-ethN) not found"
      An old bridge s1 was still there when the script started. It cleans up
      automatically, but if it persists:
          sudo ovs-vsctl --if-exists del-br s1 && sudo mn -c

  Everything FAILs in step 2 as well (not just step 1)
      The rules are not reaching the switch. Check, in a second terminal:
          sudo ovs-ofctl -O OpenFlow13 dump-flows s1
      If it is empty, ovs-ofctl could not connect - see the OVS service note
      above. Also make sure you did not edit MAC addresses in the file.

  Timings look odd / MB/s very low
      The first request after a rule change is slower, and throughput between
      virtual hosts mostly measures memory speed. Run it on an idle machine,
      and ignore absolute MB/s in a report; report the change instead.

  Ctrl-C during the run
      The script still tears down the network (its finally-block runs). If the
      terminal is killed hard, run: sudo mn -c


SMALL KNOBS (all at the top of simple_scdn.py or in one function)
-----------------------------------------------------------------
  HTTP_PORT / BIG_BYTES       port and size of the throughput file
  SERVERS / CLIENT / VIP      addressing plan (if you change MACs, change all)
  phase_distribution()        range(9)  -> number of distribution requests
  phase_failover()            range(6)  -> number of failover requests
  phase_recovery()            range(6)  -> number of recovery requests
  phase_failure()             'h3'      -> which server is killed

After editing, rerun. There is no other configuration to keep in sync.


DEMO SCRIPT FOR A 3-MINUTE PRESENTATION
---------------------------------------
  1. Show the topology diagram in README.txt section 2, and the six rules in
     section 4.
  2. "The client only knows one address, the VIP. The switch decides which
     server answers. Watch the rule change." Run the script.
  3. Point at STEP 1: no rules -> nothing works. Rules matter.
  4. Point at STEP 3: the rule->h2/h3/h4 column and the served_by column move
     together. That is the switch doing it, not the client.
  5. Point at STEP 5/6: the FAIL row, then all OK rows while h3 is still dead.
  6. Point at STEP 7 and at the summary's access-log cross-check.
  7. Open the CSV and show the same data as a table.
