
==========================================================================
STEP 0: build the topology
==========================================================================
  switch ports: h1=1, h2=2, h3=3, h4=4
  h1 (client), s1 (OpenFlow 1.3 switch), h2/h3/h4 (servers) are up.
  the client asks for 10.0.0.100, which all three servers own as a /32.

  --- how to read the numbers in this output -------------------------
  request time      measured inside h1, from the start of the TCP connect
                    to the last byte of the body.  It includes the server
                    building the reply, so it is request completion time and
                    NOT the network round trip time (RTT).
  probe time        one TCP connect to the server's OWN address, no data.
                    The probe timeout is 400 ms, so a DOWN probe near 400 ms
                    means "no packets came back" (broken path), while a DOWN
                    probe near 0 ms means "refused" (the host is fine, but
                    nothing is listening on port 8080).
  throughput        MB/s = bytes received / transfer time, with 1 MB =
                    1,000,000 bytes (decimal MB, not MiB).
  rule->hX          the server the VIP rule pointed at before the request.
  served_by=hX      the server that really answered, read from the body.
                    These two must match; a mismatch is a real bug.
  OK / FAIL         an HTTP 200 arrived / no usable answer arrived.
  2.5 s timeout     the CLIENT gave up.  That number is the client's own
                    patience, not the server's speed.
  link settle       a fixed 1500 ms pause after unplug / replug, so that
                    Open vSwitch notices the port state change.

  how to read a rule line - these numbers belong to the SWITCH, not to
  any request:
    cookie=0x0         tag Open vSwitch stamps on every rule; unused here
    duration=x.xxxs    how many seconds this rule has existed inside the
                       switch.  It is the AGE of the rule, never the time
                       a request took.

                       installed - the proof that the switch is using it
    priority=N         when several rules match one packet, the highest
                       priority wins

STEP 11: comparison - one request, five different conditions
==========================================================================
  Same client (h1), same VIP (10.0.0.100), same 13-byte file, same server
  (h3).  Only h3's cable and h3's web server differ between the rows.
  "request time" and "probe time" are defined in the header at step 0.

  condition                        h3 link h3 server result served  request time probe time
  port connected (h3 cable in)     UP      running   OK     h3           2.9 ms     0.1 ms
  port disconnected (cable pulled) DOWN    running   FAIL   -         2502.9 ms   400.9 ms
  port reconnected (cable back)    UP      running   OK     h3           2.0 ms     0.7 ms
  server process killed (h3)       UP      stopped   FAIL   -            0.2 ms     0.1 ms
  server restarted (h3)            UP      running   OK     h3           6.8 ms     0.2 ms

  what DISCONNECTING THE PORT changes:
    request time   2.9 ms -> 2502.9 ms  (+2500.0 ms, about 860x slower)
    probe time     0.1 ms -> 400.9 ms  (hits the 400 ms probe timeout)
    error          none -> TimeoutError
    why            the frame stops at the switch, so no answer and no
                   error can come back.  The 2.5 s figure is the client
                   giving up, not h3 needing that long to reply.

  what RECONNECTING THE PORT changes:
    request time   2.0 ms again and the error is gone: the repaired path
                   carries VIP traffic, with no change to the client.

  what KILLING THE SERVER PROCESS changes (cable still in):
    request time   2.9 ms -> 0.2 ms  - FASTER, not slower
    error          none -> ConnectionRefusedError
    why            the packet reaches h3 and is rejected immediately, so
                   there is no timeout to sit through.  A refused
                   connection and a dead path are different failures,
                   which is why the client reports two different errors.

  what RESTARTING THE SERVER PROCESS changes:
    request time   6.8 ms again, served_by=h3: h3 is a candidate again
                   because the next health check measured it, not because
                   any code re-enables h3.

  the one-line version for the viva:
    port disconnected -> TimeoutError after 2503 ms (nothing comes back)
    process killed    -> ConnectionRefusedError after 0.2 ms
    same user experience (a failed request), completely different cause.

  service-level comparison (does the client still get an answer?)
  window                               requests  served failed   success     mean time
  all healthy, before any failure            17      17      0      100%        2.7 ms
  h3 port pulled, policy active               5       4      1       80%        1.8 ms
  h3 process killed, policy active            7       6      1       86%        1.7 ms
  after h3 recovered                          8       8      0      100%        2.6 ms
  the failed requests in the middle windows are deliberate: the rule is
  pointed at the broken server on purpose, to show what a user would see.
  the policy itself never routes to an unhealthy server, which is why the
  requests that follow each health check are all served.
